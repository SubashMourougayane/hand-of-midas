## What Happened: First Live Trading Day

### The Good
- **System detected a legitimate bearish sweep** on window 06-10 UTC at 11:24 UTC
- Signal was valid: wick $4,404.19 > bearish level $4,399.84, bias bearish ✓, R:R 3.2:1
- **MT5 execution worked** — order placed, filled at $4,384.77

### The Bad — Duplicate Orders Crisis
- System placed **10+ duplicate positions** on the same signal
- Root cause: `lot_size NOT NULL` column missing from DB INSERT → save failed → `trades_today` always 0 → re-fired every 3 min
- Additional cause: DWX EA on 2 charts (BRENT + XAUUSD) → one command file = 2 positions
- Additional cause: Multiple windows finding same engulfing simultaneously
- Total loss from duplicates: ~$600+ on demo account

### The Ugly — Stale Signal Re-entry
- After SL hit on first trade, system re-entered the SAME stale sweep every 3 minutes
- `processed_sweeps` set resets per job run (not persistent)
- Engulfing window was 2 hours — same bar detectable for hours after price moved away
- `sl_too_close_to_price` spam (47+ signals logged)

## Bugs Fixed (in order of discovery)

| # | Bug | Impact | Fix |
|---|-----|--------|-----|
| 1 | `lot_size` missing from INSERT | DB save fails → infinite duplicate orders | Added `lot_size = units/100` |
| 2 | No try/except on DB INSERT | Function crashes, trade_ref not returned | Wrapped in try/except, always return trade_ref |
| 3 | Multiple windows fire in same cycle | 2-3 trades per scan | `trade_placed_this_cycle` flag |
| 4 | DWX EA on 2 charts | Single command = 2 positions | Removed EA from BRENT chart |
| 5 | `t["trade_id"]` vs `t["id"]` | Position monitor crashes (KeyError) | `t.get("id") or t.get("trade_id")` |
| 6 | Position monitor can't detect closure | Trades stuck as "open" in DB after SL hit | Handle None from get_trade_details as "closed" |
| 7 | No "one position at a time" guard | Re-enters while existing trade open | DB check: skip if open GD-MI-% exists |
| 8 | Same sweep re-fires after SL hit | Infinite re-entry on stale signal | 5-min cooldown after any signal attempt |
| 9 | 5-min cooldown only on `taken=True` | `sl_too_close` spam not blocked | Cooldown on taken OR order_error OR sl_too_close |
| 10 | SL too close to current price | Broker rejects (retcode=10016) | Pre-check: SL must be >$1 from current price |
| 11 | Engulfing window 2hr produces stale signals | Price moves $5-$10 from entry → bad trades | **Reduced to 45 minutes** |

## Strategy Research: Bias Filter

**Question:** Should we reverse the bias filter? (Yesterday red → go long today?)

| Mode | Trades | WR | PF | P&L (20yr) |
|------|:------:|:--:|:--:|:----------:|
| **Normal (current)** | 3,066 | **64.4%** | **3.01** | **$915,776** |
| No filter | 4,453 | 55.2% | 1.80 | $567,688 |
| Reversed | 3,892 | 49.7% | 1.39 | $150,746 |

**Normal filter is $765K better than reversed over 20 years.** Keep it.

**Key insight:** Reversal days happen 53.3% of the time (more than continuation at 46.7%). But the filter works because of OUTCOME ASYMMETRY — traps on continuation days are 3:1 profitable while losses on reversal days are small (no sweep forms = no trade = no loss).

## What's Next

### URGENT (next session — causes real money loss NOW):

**NEW CRITICAL BUG: Position monitor exit estimation is LYING about P&L**

**What happened (May 29 morning):**
- Trade 1993236309: SHORT 64 units @ $4,501.76, SL $4,511.48, TP $4,479.90
- MT5 ACTUALLY closed at SL $4,511.48 → REAL loss = **-$622**
- But position monitor said: "CLOSED: TP @ $4,479.90, P&L=$1,399.21"
- Dashboard shows +$1,399 profit when reality is -$622 LOSS
- **The estimation logic guessed WRONG.** It saw position gone, estimated TP hit, but it was SL hit.

**Root cause:** `backend-micro/scanner/live_engine.py` lines 244-269. When `get_trade_details()` returns None (trade not in open_orders.json), the code ESTIMATES the exit:
```python
if trade["side"] == "SHORT":
    if current_price >= sl_price - 5:  # Near SL
        fill_price = sl_price
    else:
        fill_price = tp_price  # ← ASSUMES TP if not near SL
```
The problem: by the time position monitor runs (1 min later), price may have MOVED AWAY from SL. At check time, price was near TP ($4,479), so it assumed TP hit. But the ACTUAL exit was SL ($4,511) which happened earlier.

**Impact:**
- Dashboard shows WRONG P&L (+$1,399 vs actual -$622 = **$2,021 discrepancy**)
- DD state updated with WRONG direction (thinks it won, actually lost)
- consecutive_losses NOT incremented (should be 1, shows 0)
- Account balance shows $10,238 when reality is $8,743 (from MT5 history)
- Second trade entered based on false confidence

**Fix needed:**
The estimation approach is fundamentally broken. Options:
1. **Read MT5 trade history** (not just open_orders.json) — DWX can provide closed trade details
2. **Don't estimate — mark as UNKNOWN** and require manual reconciliation
3. **Check both SL AND TP proximity at the TIME the trade disappeared** (not current price)
4. **Store the last known price BEFORE the trade disappeared** (track in a price cache per open trade)

**Recommended fix:** Option 4 — on each position_monitor cycle, cache `{trade_id: current_price}`. When trade disappears, compare the CACHED price (from 1 min ago) against SL/TP. The cached price is much closer to the actual exit moment than "current" price at detection time.
