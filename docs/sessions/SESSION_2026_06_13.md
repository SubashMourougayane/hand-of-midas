## Decisions Made

1. **Per-filter sequential, not parallel-batched.** User wanted clean per-filter reports + decision points. Cost: 5 hours wall-clock for 12 filters instead of 4.5 with parallel batching, but you see each filter's impact before the next one starts.

2. **Selective ship is the rule, not exception.** When a filter has mixed results across the 4 systems (Filter #5 hurt Gold Macro, Filter #6 only helped Oil Macro), ship per-system via config knobs. The 4 systems have different geometries; treat them as distinct decision units. See `feedback_selective_ship_pattern.md`.

3. **Custom replay = no.** When the parity audit's first attempt smoke test ran, the user pushed back: "this isn't using the proven path right?" — caught me reimplementing the extractor. Rewrote as a thin wrapper. **Lesson reinforced: every signal-extraction path goes through `tests/harness/parity/extractor.py`. Every fill goes through `execute_trade`. No exceptions.**

4. **No commits unless explicitly told.** Per-filter workflow includes a wait-for-user step. Telegram pings deltas; user replies "ship N" / "stash N" / "next"; only then does merge happen. Defaults to stash if user is silent (safe).

5. **Regression on midas-deploy AFTER merge** (not just on filter branch). Catches integration bugs and cross-system config leak. Validated for #5 and #6 — both clean.
