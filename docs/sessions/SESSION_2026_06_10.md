### Phase D — Defense in depth (7 layers)

3. Sweep blacklist updated BEFORE `execute_signal`
4. DWX EA preserves full comment
5. `reconcile_orphans()` every 60s in all 4 systems, idempotent ON CONFLICT, fires Telegram
6. Daily recon Telegram at 00:05 UTC per system
7. Schema VARCHAR(50) for all `strategy` columns

### Phase G — Phantom Fill Bug (BE-ambiguity variant) — Late Discovery
After the first clean post-rebuild trade fired (Gold Micro SHORT 30 oz on Gold), I wrote a postmortem claiming the trade exited at BE for +$9. **The user immediately caught it** — JustMarkets web showed TP hit for ~+$910.80, not BE+$9. They were right.

Root cause traced: `check_open_positions()` in both micro engines uses a heuristic when MT5 closes a trade and DWX has no closed-history file. The heuristic checks if `extremes['high'] >= sl_price` and `extremes['low'] <= tp_price`. When BE armed, the high recorded earlier in the trade life crosses the new (BE-moved) SL level retroactively. So both extremes register as "reached" → heuristic defaults to SL → wrong P&L.

**This is the same bug class as the May 22 backtest phantom fill.** Time-oblivious heuristics over time-aware broker truth. The May 22 fix moved backtest to bar-walking with explicit ordering. Today's fix gives live access to broker's authoritative close history.

Components shipped (`141772e`):
- `mql5/DWX_Server.mq5` — added `OnTradeTransaction` handler that captures every closed position (filtered by our magic) and appends to `closed_orders.json` with broker's actual `close_price`, `deal_reason` (TP/SL/CLIENT/SO/EXPERT), `profit`, `commission`, `swap`. Trims to last 200 entries.
- `backend/execution/mt5_executor.py` — `get_trade_details()` now checks `closed_orders.json` when trade isn't in `open_orders.json`. Returns `state='CLOSED'` with full broker data.
- `backend-micro/scanner/live_engine.py` + `backend-oil-micro/scanner/live_engine.py` — `check_open_positions()` prefers broker-authoritative data. Fallback heuristic now SKIPS ambiguous cases (both/neither reached) and retries next cycle, instead of defaulting to SL.
- `scripts/fix_GD-MI-cce2a254_phantom_fill.sql` — corrected the affected DB row (+$901.80 to Gold Micro DD state).
- `tests/harness/test_20_phantom_fill_be_ambiguity.py` — 9 regression tests.
- `docs/BUG_PHANTOM_FILL_BE_AMBIGUITY.md` — forensic record.

**User verified the deploy at session end:** SQL applied (DB shows TP+$910.80), DWX EA recompiled with new handler active, services restarted. First end-to-end test of the new path will be the NEXT trade closure.

### Phase H — Parity-risk discovery (the thing to address before next strategy change)

While the postmortem pipeline was being built, did a quick survey of how live signal-gen relates to backtest signal-gen. Found that **the 4 systems' live and backtest paths are PARALLEL implementations of the same logic, not shared code.** Configs match (per-system `config.py` imports), but the algorithms (sweep detection, engulfing pattern, bias filter, dedup, cooldown, max_trades_per_day) are reimplemented in `scanner/scheduler.py` (live) vs `backtest/engine.py` + `backend/strategies/*.py` (backtest).

This explains the 4 confirmed drift bugs of the past 3 weeks:
1. TDB (commit `c4bc1ae`) — live used server hours, backtest used real UTC
2. Oil Macro V1-only (commit `5c048f1`) — live had V1, backtest had Combined V1+V2
3. Schema VARCHAR(20) overflow (commit `c5f08ad`) — fresh deploy worked, mutation drifted
4. Phantom fill BE-ambiguity (commit `141772e`) — backtest fill walks bars in time order; live's close-detection guesses from extremes

`tests/harness/test_12_replay.py` exists but tests scheduler crash-resistance, not signal-by-signal output parity. **Building a real parity test (run same input through both paths, compare outputs) is the top architectural item for next session.** Until then, treat live and backtest as "we believe they match but have not verified."
